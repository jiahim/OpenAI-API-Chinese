# 升级到 GPT-5.4

当用户明确要求将现有集成升级到 GPT-5.4 时，请参考本指南，并结合最新的 OpenAI 文档进行查阅。默认的目标字符串为 `gpt-5.4`.

## Upgrade posture

以最小且安全的变更集进行升级：

- 先替换模型字符串
- 仅更新与该模型使用直接相关的提示词
- 在可行时优先采用仅升级提示词的方案
- 如果升级需要 API 表面的改动、参数重写、工具重连或更广泛的代码修改，请将其标记为阻止，而不是扩展范围

## 升级 工作流

1. 盘点当前的模型使用情况。
   - 搜索模型字符串、客户端调用以及包含提示的文件。
   - 当内联提示、提示模板、YAML 或 JSON 配置文件、Markdown 文档以及已保存的提示与某个模型使用位置明确关联时，将它们一并纳入。
2. 将每个模型使用与其提示面一一对应。
   - 优先选择最近的提示面：首先看内联的系统或开发者文本，然后是相邻的提示文件，最后是共享模板。
   - 如果无法明确地将提示与模型使用关联起来，请如实说明，而不是猜测。
3. 对源模型系列进行分类。
   - 常见分类： `gpt-4o` 或 `gpt-4.1`, `o1` 或 `o3` 或 `o4-mini`，早期 `gpt-5`，较晚 `gpt-5.x`，或混合且不明。
4. 确定升级类别。
   - `model string only`
   - `model string + light prompt rewrite`
   - `blocked without code changes`
5. 运行无代码兼容性检查。
   - 检查当前集成是否可以在无需API层面的改动或实现变更的情况下接受 `gpt-5.4` ，而无需接口层面的改动或实现变更。
   - 对于长时间运行的 Responses 或大量使用工具的智能体，检查在主机回放助手条目或使用开场白时， `phase` 是否已被保留或在往返过程中得以保留。
   - 如果兼容性依赖于代码改动，则返回 `blocked`.
   - 如果兼容性不明，则返回 `unknown` 而不是临时发挥。
6. 建议升级。
   - 默认替换字符串： `gpt-5.4`
   - 保持改动尽可能小，且不改变行为。
7. 给出结构化的推荐。
   - `Current model usage`
   - `Recommended model-string updates`
   - `Starting reasoning recommendation`
   - `Prompt updates`
   - `Phase assessment` 当流程运行时间较长、需要重放或工具调用密集时
   - `No-code compatibility check`
   - `Validation plan`
   - `Launch-day refresh items`

输出规则：

- 始终为每个使用位置发出一个起始值 `reasoning_effort_recommendation` 。
- 如果仓库公开了当前的推理设置，则优先保留它，除非源指南另有说明。
- 如果仓库未公开当前设置，则使用源系列的起始映射，而不是返回 `null`.

## 升级成果

### `model string only`

适用场景：

- 现有提示已经简短、明确且任务边界清晰
- 该工作流并非重度依赖研究、工具、多智能体、批处理或完整性敏感型，也不是长周期任务
- 不存在明显的兼容性问题

默认操作：

- 将模型字符串替换为 `gpt-5.4`
- 保持提示词不变
- 使用现有评估或抽查验证行为

### `model string + light prompt rewrite`

适用场景：

- 旧提示词是为了弥补较弱的指令遵循能力
- 该工作流需要比默认工具使用行为可能提供的更强的持续性
- 任务需要更强的完成度、引用规范或验证
- 升级后的模型会变得过于冗长或不够完整，除非另有指示
- 该工作流以研究为主,需要更强地处理稀疏或为空的检索结果
- 该工作流面向编码、工具密集或多智能体场景，但现有的API接口和工具定义可以保持不变

默认操作：

- 将模型字符串替换为 `gpt-5.4`
- 添加一两个有针对性的提示词块
- 阅读 [GPT-5.4 提示词最佳实践](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.4#prompting-best-practices) 以选择恢复旧行为所需的最小的提示词修改
- 避免与升级无关的大范围提示词清理
- 对于研究类工作流，默认使用 `research_mode` + `citation_rules` + `empty_result_handling`；在 `tool_persistence_rules` 时添加（如果宿主已经在使用检索工具）
- 对于依赖感知或工具密集型工作流，默认使用 `tool_persistence_rules` + `dependency_checks` + `verification_loop`；在 `parallel_tool_calling` 仅当检索步骤真正独立时
- 对于编码或终端类工作流，默认使用 `terminal_tool_hygiene` + `verification_loop`
- 对于多智能体支持或分诊工作流，默认至少启用以下其中一项 `tool_persistence_rules`, `completeness_contract`，或 `verification_loop`
- 对于包含前言或多条助手消息的长时间运行的 Responses 智能体，明确审视是否 `phase` 已经处理过；如果新增或保留 `phase` 需要修改代码，则将该路径标记为 `blocked`
- 不要仅因可见代码片段极少，就把编码或工具调用的 Responses 工作流归类为 `blocked` ；应优先选择 `model string + light prompt rewrite` ，除非仓库明确显示安全的 GPT-5.4 路径需要宿主侧代码变更

### `blocked`

适用场景：

- 升级似乎需要 API 层面的变更
- 升级似乎需要在实现代码之外无法暴露的参数重写或推理设置变更
- 升级需要更改工具定义、工具处理器接线或 schema 契约
- 你无法可靠地识别与该模型使用相关的提示面

默认操作：

- 不要即兴提出更宽泛的升级方案
- 报告此阻塞点，并说明该修复超出了本指南的范围

## 无代码兼容性清单

在推荐免升级方案前，请先检查：

1. 当前宿主能否接受 `gpt-5.4` 模型字符串而无需修改客户端代码或 API 接口？
2. 相关的提示词是否可识别且可编辑？
3. 宿主是否依赖于可能需要 API 接口变更、参数重写或工具重新连接的行为？
4. 可行的修复是仅修改提示词，还是需要进行实现层面的改动？
5. 提示词的使用面与模型用法是否足够接近，以便你进行定向修改而非大范围清理？
6. 对于长时间运行的 Responses 或工具密集的 智能体，是否 `phase` 在宿主依赖于前导消息、重放的助手消息项或多条助手消息时已经得到保留？

如果第 1 项为否，第 3 至第 4 项指向实施工作，或者第 6 项为否且修复需要代码更改，则返回 `blocked`.

如果第 2 项为否，则返回 `unknown` 除非用户能够指出提示词所在位置。

重要：

- 现有的工具、智能体或多个使用点本身并不是阻碍因素。
- 如果当前宿主可以保留相同的 API 表面和相同的工具定义，则优先选择 `model string + light prompt rewrite` 而非 `blocked`.
- 将保留 `blocked` 用于确实需要更改实现的情况，而非仅需要更强提示引导的情况。

## 范围边界

本指南可能：

- 更新或推荐更新后的模型字符串
- 更新或推荐更新后的提示
- 检查代码和提示文件，以了解这些更改应归属的位置
- 检查现有 Responses 流程是否已保留 `phase`
- 标记兼容性阻塞项

本指南不得：

- 将 Chat Completions 代码迁移到 Responses
- 将 Responses 代码迁移到其他 API 接口
- 重写参数结构
- 更改工具定义或工具调用处理方式
- 更改结构化输出接入方式
- 新增或改造 `phase` 实现代码中的处理逻辑
- 编辑业务逻辑、编排逻辑或 SDK 用法（超出字面模型字符串替换的范围）

如果安全的 GPT-5.4 升级需要进行上述任何更改,请将该路径标记为阻塞并标为超出范围。

## 验证计划

- 使用现有的评估或真实的抽查来验证每个升级后的使用点。
- 检查升级后的模型是否仍然符合预期的延迟、输出形态和质量。
- 如果新增了提示词编辑，请确认每个模块都在真正发挥作用，而不是增加噪声。
- 如果 工作流 存在下游影响，请在最终化之前添加一次轻量级的验证流程。

## 发布日刷新项

当 GPT-5.4 最终指引发生变化时：

1. 在适当的位置使用最终的 GPT-5.4 指引替换候选发布版本的假设。
2. 重新检查默认目标字符串是否应保持不变 `gpt-5.4` 适用于所有来源系列。
3. 重新检查任何语义可能已发生变化的提示块相关建议。
4. 根据最终模型行为重新检查研究、引用和兼容性相关指引。
5. 重新运行相同的升级场景，并确认受阻与可行的边界仍然成立。
