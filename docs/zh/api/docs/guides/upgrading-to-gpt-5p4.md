# 升级到 GPT-5.4

当用户明确要求将现有集成升级到 GPT-5.4 时，请使用本指南。将其与当前的 OpenAI 文档查询配合使用。默认目标字符串为 `gpt-5.4`.

## 升级姿态

使用范围最窄的安全变更集进行升级：

- 首先替换模型字符串
- 仅更新与该模型使用直接相关的提示词
- 可能时优先仅升级提示词
- 如果升级需要 API 表面更改、参数重写、工具重新接线或更广泛的代码编辑，则将其标记为阻塞，而不是扩大范围

## 升级工作流

1. 盘点当前的模型使用情况。
   - 搜索模型字符串、客户端调用以及包含提示词的文件。
   - 当内联提示词、提示词模板、YAML 或 JSON 配置、Markdown 文档以及保存的提示词明确与某个模型使用位置相关时，将其一并纳入。
2. 将每个模型使用与其提示词界面配对。
   - 优先选择最接近的提示词界面：首先是内联系统或开发者文本，其次是相邻的提示词文件，最后是共享模板。
   - 如果你无法自信地将某个提示词与模型使用关联起来，应如实说明，而不是猜测。
3. 对源模型系列进行分类。
   - 常见的分类有： `gpt-4o` 或 `gpt-4.1`, `o1` 或 `o3` 或 `o4-mini`、早期 `gpt-5`、后期 `gpt-5.x`，或混合且不明确。
4. 确定升级类别。
   - `model string only`
   - `model string + light prompt rewrite`
   - `blocked without code changes`
5. 运行无代码兼容性门禁。
   - 检查当前集成是否可以接受 `gpt-5.4` 而无需API层面的变更或实现变更。
   - 对于长时间运行的 Responses 或工具密集型智能体，检查 `phase` 在宿主重放助手项目或使用前导时是否已保留或往返传递。
   - 如果兼容性取决于代码更改，请返回 `blocked`.
   - 如果兼容性不明确，请返回 `unknown` 而不是自行尝试。
6. 建议升级。
   - 默认替换字符串： `gpt-5.4`
   - 保持干预最小化并保持行为不变。
7. 提供结构化的建议。
   - `Current model usage`
   - `Recommended model-string updates`
   - `Starting reasoning recommendation`
   - `Prompt updates`
   - `Phase assessment` 当流程是长时间运行、重放或大量使用工具时
   - `No-code compatibility check`
   - `Validation plan`
   - `Launch-day refresh items`

输出规则：

- 始终以起始 `reasoning_effort_recommendation` 用于每个使用位置。
- 如果仓库暴露了当前的推理设置，除非源指南另有说明，否则先保留该设置。
- 如果仓库未暴露当前设置，则使用源系列起始映射，而非返回 `null`.

## 升级成果

### `model string only`

在以下情况下选择此选项：

- 现有提示词已经足够简短、明确且任务边界清晰
- 该工作流并非强研究型、强工具型、多智能体、批处理或完整性敏感型，也非长周期型
- 不存在明显的兼容性障碍

默认操作：

- 将模型字符串替换为 `gpt-5.4`
- 保持提示词不变
- 使用现有评估或抽查来验证行为

### `model string + light prompt rewrite`

在以下情况下选择此方案：

- 旧提示词是为了弥补指令遵循能力较弱的问题
- 该工作流需要的持久性可能超出默认工具调用行为所能提供的程度
- 任务需要更强的完整性、引用纪律或验证
- 除非另有指示，升级后的模型会变得过于冗长或不完整
- 该工作流研究密集，需要更好地处理稀疏或空检索结果
- 该工作流面向编码、工具密集或多智能体，但现有的API表面和工具定义可以保持不变

默认操作：

- 将模型字符串替换为 `gpt-5.4`
- 添加一个或两个针对性的提示块
- 阅读 [GPT-5.4 的提示最佳实践](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.4#prompting-best-practices) 选择能恢复旧行为的最小提示更改
- 避免与升级无关的宽泛提示清理
- 对于研究工作流，默认使用 `research_mode` + `citation_rules` + `empty_result_handling`；添加 `tool_persistence_rules` 当主机已使用检索工具时
- 对于依赖感知或工具密集型工作流，默认使用 `tool_persistence_rules` + `dependency_checks` + `verification_loop`；添加 `parallel_tool_calling` 仅当检索步骤真正独立时
- 对于编码或终端工作流，默认使用 `terminal_tool_hygiene` + `verification_loop`
- 对于多智能体支持或分流工作流，默认至少使用以下之一 `tool_persistence_rules`, `completeness_contract`，或 `verification_loop`
- 对于带有前导语或多条助手消息的长时间运行的 Responses 智能体，明确审查是否 `phase` 已处理；如果添加或保留 `phase` 将需要代码编辑，则将该路径标记为 `blocked`
- 不要将编码或使用工具的 Responses 工作流 分类为 `blocked` 仅因为可见片段最小；优先选择 `model string + light prompt rewrite` 除非仓库明确显示安全 GPT-5.4 路径需要主机端代码更改

### `blocked`

在以下情况下选择此选项：

- 升级似乎需要 API 层面的变更
- 升级似乎需要参数重写或推理设置变更，而这些在实现代码之外不可见
- 升级将需要更改工具定义、工具处理器接线或模式契约
- 你无法可靠地识别与模型使用关联的提示词层面

默认操作：

- 不要即兴进行更广泛的升级
- 报告阻塞问题，并说明修复超出本指南的范围

## 无代码兼容性清单

在推荐无代码升级之前，请检查：

1. 当前主机能否在不更改客户端代码或 API 表面的情况下接受 `gpt-5.4` 模型字符串？
2. 相关提示是否可识别且可编辑？
3. 主机是否依赖于可能需要 API 表面更改、参数重写或工具重新布线的行为？
4. 可能的修复是否仅涉及提示，还是需要实现更改？
5. 提示表面是否与模型使用足够接近，以便你可以进行有针对性的更改，而不是进行广泛的清理？
6. 对于长时间运行的 Responses 或工具密集的 智能体，如果主机依赖前言、重放的助手项或多个助手消息， `phase` 是否已经保留？

如果第 1 项为否，第 3 至第 4 项指向实施工作，或者第 6 项为否且修复需要代码更改，则返回 `blocked`.

如果第 2 项为否，则返回 `unknown` 除非用户能指明提示位置。

重要：

- 现有的工具、智能体或多种使用场景本身并不是阻碍因素。
- 如果当前宿主可以保持相同的API表面和相同的工具定义，优先选择 `model string + light prompt rewrite` 而非 `blocked`.
- 保留 `blocked` 用于真正需要实现变更的情况，而非仅需更强提示词引导的情况。

## 作用域边界

本指南可能：

- 更新或推荐更新的模型字符串
- 更新或推荐更新的提示词
- 检查代码和提示词文件，了解这些更改应归属何处
- 检查现有的 Responses 流程是否已保留 `phase`
- 标记兼容性阻塞问题

本指南可能不会：

- 将 Chat Completions 代码迁移到 Responses
- 将 Responses 代码迁移到其他 API 表面
- 重写参数形状
- 更改工具定义或工具调用处理
- 更改结构化输出接线
- 添加或改造 `phase` 实现代码中的处理
- 编辑业务逻辑、编排逻辑或 SDK 的使用，超出字面模型字符串替换的范围

如果安全的 GPT-5.4 升级需要任何这些更改，请将该路径标记为受阻且不在范围内。

## 验证计划

- 使用现有的评估或现实抽查来验证每个升级后的使用位置。
- 检查升级后的模型是否仍然符合预期的延迟、输出形状和质量。
- 如果添加了提示词编辑，确认每个块都在做实际工作而不是增加噪音。
- 如果工作流有下游影响，在最终确定前添加一个轻量级验证环节。

## 发布日刷新项

当最终 GPT-5.4 指南发生变化时：

1. 在适当时，将候选发布版本的假设替换为最终的 GPT-5.4 指南。
2. 重新检查默认目标字符串是否应保持 `gpt-5.4` 适用于所有源系列。
3. 重新检查语义可能已更改的任何提示块建议。
4. 重新检查研究、引用和兼容性指南与最终模型行为的一致性。
5. 重新运行相同的升级场景，并确认阻止与可行的边界仍然成立。
