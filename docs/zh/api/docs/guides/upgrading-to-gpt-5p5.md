> 完整的文档索引，请参阅 [llms.txt](/llms.txt)。文档页面的 Markdown 版本可通过在页面 URL 后追加 `.md` 来获取。

# 升级到 GPT-5.5

当用户明确要求将现有集成升级到 GPT-5.5 时，使用本指南。将其与当前的 OpenAI 文档查询配对。默认目标字符串是 `gpt-5.5`.

## 升级姿态

使用最窄的安全变更集进行升级：

- 先替换模型字符串
- 只更新与该模型使用直接相关的提示词
- 不要自动升级较旧的或可能存在有意固定的模糊模型用法，例如历史文档、示例、测试、评估基线、对比代码或低成本回退/路由路径。除非用户明确要求升级所有模型用法，否则保持这些位置不变，并将其列为需确认项
- 尽可能优先采用仅提示词升级
- 如果升级需要API表面变更、参数重写、工具重新接线、提供商迁移或更广泛的代码编辑，则将其标记为受阻，而不是扩大范围

## 升级工作流

1. 盘点当前模型使用情况。
   - 搜索模型字符串、客户端调用和包含提示的文件。
   - 包括内联提示、提示模板、YAML 或 JSON 配置、Markdown 文档和保存的提示，只要它们明显与模型使用位置相关联。
2. 将每个模型用途与其提示面配对。
   - 优先使用最近的提示面：内联系统或开发者文本，然后是相邻的提示文件，最后是共享模板。
   - 如果无法确信地将提示与模型使用关联，请明确说明，而不是猜测。
3. 对源模型系列进行分类。
   - 常见类别：GPT-5.4、GPT-5.3-Codex 或 GPT-5.2-Codex、较早的 GPT-5.x、GPT-4o 或 GPT-4.1、推理模型（如 o1、o3 或 o4-mini）、第三方模型，或混合且不明确的类别。
4. 确定升级类别。
   - `model string only`
   - `model string + light prompt rewrite`
   - `blocked without code changes`
5. 运行兼容性检查。
   - 检查当前集成是否可以接受 `gpt-5.5` ，无需 API 层变更或实现变更。
   - 检查结构化输出、工具模式、函数名称和下游解析器是否可以保持不变。
   - 对于长时间运行的 Responses 或工具密集型的 智能体，检查 `phase` 在宿主重放助理消息或使用前导内容时，是否已保留或进行往返。
   - 如果兼容性依赖于代码更改，请返回 `blocked`.
   - 如果兼容性不明确，请返回 `unknown` ，而不是即兴发挥。
6. 在范围内时应用升级。
   - 默认替换字符串： `gpt-5.5`.
   - 保持干预动作小而符合原有行为。
   - 当推理强度可见时，从当前推理强度出发，除非有确切理由需要修改。
   - 对于范围内的更改，更新模型字符串及直接相关的提示词。
   - 对于被阻止或未知的更改，不要编辑；报告阻止原因或不确定性。
7. 总结结果。
   - `Current model usage`
   - `Model-string updates`
   - `Reasoning-effort handling`
   - `Prompt updates`
   - `Structured output and formatting assessment`
   - `Tool-use assessment` 当流程使用工具、检索或终局操作时
   - `Phase assessment` 当流程为长时间运行、可重放或工具密集型时
   - `Compatibility check`
   - `Validation performed`

输出规则：

- 对于每个使用场景，请说明初始的推理工作量建议。
- 如果仓库暴露了当前的推理设置，除非当前 OpenAI 文档另有说明，否则建议首先保留该设置。
- 如果仓库未暴露当前设置，则建议不要添加，除非当前 OpenAI 文档要求这样做。

## 升级成果

### `model string only`

在以下情况下选择此方案：

- 源模型是 GPT-5.4
- 现有提示词已经简短、明确且任务边界清晰
- 该工作流不依赖于严格的输出格式、工具调用行为、批次完整性或应在升级后验证的长周期执行
- 没有明显的兼容性阻塞项

默认操作：

- 将模型字符串替换为 `gpt-5.5`
- 保持当前的推理努力程度
- 保持提示词不变
- 使用现有测试、实际抽查或（如已有）现有评估套件来验证行为

### `model string + light prompt rewrite`

在以下情况选择此选项：

- 任务需要更强的完整性、引用纪律、验证或依赖处理能力
- 升级后的模型变得过于冗长、过于密集或难以快速浏览，除非对格式加以约束
- 该工作流对输出形状有严格要求，且缺乏明确的格式约定、模式或解析器验证
- 该工作流研究密集，需要更好地处理稀疏或空检索结果
- 该工作流以编码为导向、基于终端、工具密集或多智能体，但现有API面和工具定义可以保持不变

默认操作：

- 将模型字符串替换为 `gpt-5.5`
- 在第一次传递中保留当前的推理努力
- 仅对观察到的 工作流 风险进行必要的最小提示词编辑
- 阅读 [GPT-5.5 提示词最佳实践](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.5#prompting-best-practices) 以选择能恢复或改善行为的最小提示词更改
- 避免与升级无关的广泛提示词清理
- 对于研究工作流，根据提示指南添加引用规则、检索预算、缺失证据行为和验证指导
- 对于依赖感知或工具密集型工作流，添加前置条件检查、缺失上下文处理、明确的工具预算、停止条件和验证指导
- 对于编码或终端工作流，添加仓库特定约束、验收标准和具体验证命令
- 对于多智能体支持或分诊工作流，添加任务所有权、交接、完整性和停止标准
- 对于带有前言或多条助手消息的长运行 Responses 智能体，明确审查是否 `phase` 已经处理；如果添加或保留 `phase` 需要代码编辑，将该路径标记为 `blocked`
- 不要将编码或使用工具的 Responses 工作流 分类为 `blocked` 仅因为可见片段过于简短；偏好 `model string + light prompt rewrite` 除非仓库明确显示安全的 GPT-5.5 路径需要主机端代码更改

### `blocked`

在以下情况中选择此项：

- 该升级似乎需要 API 层面的变更
- 该升级似乎要求重写参数或更改推理设置，这些在实现代码之外不可见
- 该升级将要求更改工具定义、工具处理器接线或模式合同
- 用户要求的是工具、IDE、插件、Shell 或环境的迁移，而非模型和提示词的迁移
- 该集成依赖于特定于提供商的 API，这些  无法映射到当前 OpenAI API 层面而不进行实现工作
- 你无法确定地识别与模型使用相关的提示词层面

默认操作：

- 不要即兴进行更广泛的升级
- 报告阻碍因素，并说明修复超出本指南的范围
- 如有帮助，描述能解锁迁移的最小的后续实施任务

## 兼容性检查清单

在应用或推荐仅模型与提示词的升级之前，请检查：

1. 当前主机能否在 `gpt-5.5` 不更改客户端代码或 API 表面的情况下接受模型字符串？
2. 相关提示是否可识别且可编辑？
3. 主机是否依赖可能需要 API 表面更改、参数重写、提供商迁移或工具重新接线的行为？
4. 可能的修复是否仅限于提示，还是需要实现更改？
5. 提示表面是否足够接近模型用法，以便你可以进行有针对性的更改，而不是进行大规模清理？
6. 严格的结构化输出、模式或下游解析器是否仍有明确的契约？
7. 对于长时间运行的 Responses 或大量使用工具的 智能体，是否 `phase` 已保留，如果主机依赖前导、重放的助手项或多个助手消息？
8. 延迟、令牌或价格假设是否通过测试、现实的抽查或现有的评估套件进行验证，而不是根据一般模型定位推断？

如果第 1 项为否，第 3 至 4 项指向实现工作，或第 7 项为否且修复需要代码更改，则返回 `blocked`.

如果第 2 项为否，则返回 `unknown` 除非用户能够指出提示位置。

重要：

- 现有的工具使用、智能体或多个使用场景本身并不是阻碍因素。
- 如果当前宿主可以保持相同的API表面和相同的工具定义，优先选择 `model string + light prompt rewrite` 而非 `blocked`.
- 保留 `blocked` 用于那些真正需要实现变更的情况，而不是仅需更强的提示词引导的情况。
- 未经任务级验证，不要声称节省了令牌。

## 范围边界

本指南可能：

- 更新或推荐更新的模型字符串
- 更新或推荐更新的提示词
- 检查代码和提示词文件，了解这些更改应归属于何处
- 检查现有的 Responses 流程是否已保留 `phase`
- 标记兼容性障碍
- 建议使用现有测试、现实抽查或现有评估套件进行验证

本指南可能不会：

- 将 Chat Completions 代码迁移至 Responses
- 将 Responses 代码迁移至另一 API 表面
- 迁移 SDK、API、IDE 配置、shell 钩子、插件或特定于提供商的工具
- 重写参数形状
- 更改工具定义或工具调用处理
- 更改结构化输出接线
- 添加或改造 `phase` 在实现代码中的处理
- 编辑业务逻辑、编排逻辑、SDK 用法、IDE 配置、shell 钩子或插件集成行为，但模型字符串替换和直接相关的提示编辑除外

如果安全的 GPT-5.5 升级需要上述任何更改，请将该路径标记为受阻且不在范围内。

## 验证计划

- 使用现有测试、实际抽查或（如果已有）现有评估套件来验证每个升级后的使用位置。
- 在可用时，与当前的 GPT-5.4 基线进行比较。
- 检查任务成功率、重试次数、工具调用次数、总令牌数、延迟、输出结构和用户可见质量。
- 对于专业工作流，验证最重要的一致性，而不仅仅判断整体输出质量。
- 如果添加了提示词编辑，请确认每个块都在做实际工作，而不是增加噪声。
- 如果工作流有下游影响，请在定稿前添加一个轻量级验证环节。
