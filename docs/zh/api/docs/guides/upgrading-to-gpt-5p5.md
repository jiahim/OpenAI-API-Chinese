# 升级到 GPT-5.5

当用户明确要求将现有集成升级到 GPT-5.5 时，请参考本指南。将其与最新的OpenAI文档查阅配合使用。默认的目标字符串为 `gpt-5.5`.

## Upgrade posture

使用最小且安全的变更集进行升级：

- 先替换模型字符串
- 仅更新与该模型使用直接相关的提示词
- 不要自动升级可能是有意锁定的旧模型或模糊模型用法，例如历史文档、示例、测试、评估基线、对比代码或低成本回退/路由路径。除非用户明确要求升级所有模型用法，否则这些位置应保持不变，并将其列为需要确认的项
- 在可能的情况下优先仅升级提示词
- 如果升级需要API层面的更改、参数重写、工具重新接线、提供商迁移或更广泛的代码编辑，应将其标记为受阻，而不是扩大范围

## 升级 工作流

1. 盘点当前的模型使用情况。
   - 搜索模型字符串、客户端调用以及包含提示的文件。
   - 当内联提示、提示模板、YAML 或 JSON 配置文件、Markdown 文档以及已保存的提示与模型使用位置明确关联时，将它们一并纳入。
2. 将每个模型使用情况与其提示表面进行配对。
   - 优先选择最近的提示表面：内联的系统或开发者文本、相邻的提示文件，然后是共享模板。
   - 如果无法确定地将提示与模型使用情况关联起来，请如实说明，而不是猜测。
3. 对源模型族进行分类。
   - 常见类别：GPT-5.4、GPT-5.3-Codex 或 GPT-5.2-Codex、更早的 GPT-5.x、GPT-4o 或 GPT-4.1、诸如 o1 或 o3 或 o4-mini 的推理模型、第三方模型，或混合与不明确。
4. 确定升级类别。
   - `model string only`
   - `model string + light prompt rewrite`
   - `blocked without code changes`
5. 运行兼容性检查。
   - 检查当前集成能否在不改动 API 接口或代码实现的情况下接收 `gpt-5.5` 而不需要对 接口 表面或实现进行更改。
   - 检查结构化输出、工具架构、函数名以及下游解析器是否可以保持不变。
   - 对于长时间运行的 Responses 或工具密集型的 智能体，检查当宿主重放助手项或使用前导消息时， `phase` 是否已被保留或往返保留。
   - 如果兼容性依赖于代码更改，则返回 `blocked`.
   - 如果兼容性不明确，则返回 `unknown` 而不是临时拼凑。
6. 在升级范围内时应用该升级。
   - 默认替换字符串： `gpt-5.5`.
   - 保持干预精简且不改变行为。
   - 在当前推理力度可见时沿用该值，除非有充分的实测理由再作调整。
   - 对于范围内（in-scope）的变更，更新模型字符串以及直接相关的 prompt。
   - 对于被阻断或未知的变更，不要编辑；报告阻断原因或不确定项。
7. 汇总结果。
   - `Current model usage`
   - `Model-string updates`
   - `Reasoning-effort handling`
   - `Prompt updates`
   - `Structured output and formatting assessment`
   - `Tool-use assessment` 当流程使用工具、检索或终止动作时
   - `Phase assessment` 当流程长时间运行、需要回放或重度依赖工具时
   - `Compatibility check`
   - `Validation performed`

输出规则：

- 针对每个使用站点，给出起始推理投入程度的建议。
- 如果仓库暴露了当前的推理设置，建议先予以保留，除非当前的 OpenAI 文档另有说明。
- 如果仓库未暴露当前设置，建议不要新增设置，除非当前 OpenAI 文档要求这样做。

## 升级效果

### `model string only`

在以下情况下选择此项：

- 源模型为 GPT-5.4
- 现有的提示词已经足够简短、明确，且任务范围有限
- 该工作流不依赖于严格的输出格式、工具调用行为、批量完整性或长周期执行，因此这些方面应在升级后再进行验证
- 不存在明显的兼容性阻塞问题

默认动作：

- 替换模型字符串 `gpt-5.5`
- 保留当前的推理强度
- 保持提示词不变
- 使用现有测试、真实的抽查，或在已有评估套件时直接复用，以验证行为

### `model string + light prompt rewrite`

在以下情况下选择此项：

- 任务需要更强的完整性、引文规范性、验证或依赖处理能力
- 升级后的模型变得过于冗长、过于密集，或难以快速浏览，除非对格式加以约束
- 工作流 对输出格式有严格要求，且缺少明确的格式契约、模式定义或解析器校验
- 工作流 以研究为主，需要更强地处理稀疏或为空的检索结果
- 工作流 以编码、终端、工具密集或多智能体协作 为主，但现有 API 接口和工具定义可以保持不变

默认动作：

- 替换模型字符串 `gpt-5.5`
- 在第一轮中保留当前的推理强度
- 仅针对观察到的 工作流 风险进行最小必要的提示词修改
- 阅读 [GPT-5.5 提示词最佳实践](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.5#prompting-best-practices) 以选择能恢复或改进行为的最小提示词改动
- 避免与本次升级无关的大范围提示词清理
- 对于研究类工作流，补充引文规则、检索预算、缺失证据时的行为以及来自提示词指南的验证指导
- 对于依赖感知或工具密集的工作流，补充前置依赖检查、缺失上下文的处理方式、明确的工具预算、停止条件以及验证指导
- 对于编码或终端工作流，补充仓库专属约束、验收标准以及具体的验证命令
- 对于多智能体 支持或任务分派工作流，补充任务归属、交接、完整性以及停止条件
- 对于带有开场白或多条助手消息的长时间运行的 Responses 智能体，请显式评估是否需要 `phase` 已经被处理;如果新增或保留 `phase` 需要代码修改,将该路径标记为 `blocked`
- 不要因为可见的代码片段很短,就把使用代码或工具的 Responses 工作流 归类为 `blocked` 只要可见代码片段很短;优先采用 `model string + light prompt rewrite` 除非仓库明确表明,安全的 GPT-5.5 路径需要宿主机端的代码修改

### `blocked`

在以下情况下选择此项：

- 升级似乎需要 API 接口层面的变更
- 升级似乎需要重写参数或修改推理相关设置,而这些改动在实现代码之外没有暴露
- 升级需要修改工具定义、工具处理器接线或 schema 契约
- 用户请求的是工具链、IDE、插件、Shell 或环境的迁移,而非模型与提示词的迁移
- 集成依赖特定提供方的 API,这些 OpenAI API 接口无法在不进行实现工作的前提下直接对应
- 无法可靠地识别与该模型使用方式绑定的提示词接口面

默认动作：

- 不要即兴给出更大范围的升级方案
- 上报该阻塞点,并说明该修复不在本指南范围内
- 如有需要,可描述能够解除此次迁移阻塞的最小后续实现任务

## 兼容性检查清单

在应用或推荐仅升级模型和提示词之前，请检查：

1. 当前宿主能否在不修改客户端代码或API接口的前提下接受 `gpt-5.5` 模型字符串？
2. 相关的提示词是否可识别且可编辑？
3. 宿主是否依赖那些可能需要API接口变更、参数重写、提供商迁移或工具重新接入的行为？
4. 可能的修复是仅修改提示词，还是需要改动实现？
5. 提示词表面与模型用法是否足够接近，使你可以进行有针对性的修改而非大范围清理？
6. 严格的结构化输出、schema 或下游解析器是否仍存在明确的契约？
7. 对于长时间运行的 Responses 或工具密集型智能体，是否 `phase` 在宿主依赖前言、重放的助手条目或多条助手消息时仍能保留？
8. 关于延迟、token 或价格的假设，是否由测试、真实的抽查或现有的评测套件验证过，而非仅凭对模型的总体定位推断得出？

如果第 1 项为否，第 3 至 4 项指向实现工作，或第 7 项为否且修复需要代码变更，则返回 `blocked`.

如果第 2 项为否，则返回 `unknown` 除非用户能指出该提示所在位置。

重要：

- 现有工具、智能体或多个使用站点的使用本身并不是阻碍因素。
- 如果当前宿主可以保持相同的 API 接口和相同的工具定义，则优先选择 `model string + light prompt rewrite` 而非 `blocked`.
- 保留 `blocked` 用于确实需要实现变更的场景，而不是仅需要更强提示引导的场景。
- 不要在未经任务级验证的情况下声称节省了 token。

## 范围边界

本指南可以：

- 更新或推荐更新后的模型字符串
- 更新或推荐更新后的提示
- 检查代码和提示文件，以确定这些更改应归属的位置
- 检查现有的 Responses 流程是否已经保留 `phase`
- 标记兼容性阻塞项
- 建议使用现有测试、实际抽查或现有评估套件进行验证

本指南可能不会：

- 将 Chat Completions 代码迁移到 Responses
- 将 Responses 代码迁移到其他 API 接口
- 迁移 SDK、API、IDE 配置、shell 钩子、插件或特定于提供方的工具
- 重写参数结构
- 更改工具定义或工具调用处理
- 更改结构化输出接线
- 新增或改造 `phase` 处理逻辑的实现代码
- 编辑业务逻辑、编排逻辑、SDK 使用方式、IDE 配置、shell 钩子或插件集成行为（模型字符串替换以及与之直接相关的提示编辑除外）

如果安全的 GPT-5.5 升级需要进行上述任何更改，请将相关路径标记为阻塞并超出范围。

## Validation plan

- 使用现有测试、真实的抽查，或在已有评估套件时复用它，对每个升级后的使用点进行验证。
- 在条件允许时与当前 GPT-5.4 基线进行对比。
- 检查任务成功率、重试次数、工具调用次数、总令牌数、延迟、输出形态以及用户可见的质量。
- 对于专业化的工作流，验证最关键的那项契约，而不是只评判通用的输出质量。
- 如果新增了提示词编辑，请确认每个模块都在真正发挥作用，而不是在增加噪声。
- 如果该工作流具有下游影响，请在最终化之前增加一轮轻量级的验证。
