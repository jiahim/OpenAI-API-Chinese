# 评估最佳实践

> 如需查看完整文档索引，请参阅 [llms.txt](/llms.txt)。文档页面的 Markdown 版本可通过在页面 URL 后追加 `.md` 获取。

生成式 AI 具有不确定性。模型有时会对相同的输入产生不同的输出，这使得传统的软件测试方法不足以应对 AI 架构。针对这种情况，评估（**evals**）是一种测试你的 AI 系统的手段。

本指南提供了设计评估的高层指导。若要开始使用 [Evals API](https://developers.openai.com/api/reference/resources/evals)，请参阅 [评估模型性能](https://developers.openai.com/api/docs/guides/evals).

## 什么是 evals？

Evals 是用于衡量模型性能的结构化测试。尽管 AI 系统具有非确定性，它们仍有助于确保准确性、性能和可靠性。它们也是少数几种能够 _提升_ 基于 LLM 的应用性能的方式之一（通过 [微调](https://developers.openai.com/api/docs/guides/model-optimization)).

### 评估类型

当你看到 "evals" 这个词时,它可能指代以下几种含义：

- 用于在隔离环境中比较模型的行业基准，例如 [MMLU](https://github.com/openai/evals/blob/main/examples/mmlu.ipynb) 以及 [HuggingFace 的排行榜](https://huggingface.co/collections/open-llm-leaderboard/the-big-benchmarks-collection-64faca6335a7fc7d4ffe974a)
- 标准数值分数——例如 [ROUGE](https://aclanthology.org/W04-1013/), [BERTScore](https://arxiv.org/abs/1904.09675)——在为你的用例设计评估时可以使用
- 你为衡量 LLM 应用程序性能而实现的具体测试

本指南介绍的是第三种类型：设计你自己的 evals。

### 如何阅读 evals

你经常会看到介于 0 到 1 之间的数值评测分数。评测不仅仅是分数这么简单。将指标与人工判断结合起来，确保你在回答正确的问题。

**评测技巧**


- 采用评估驱动的开发：尽早并频繁地评估。在每个阶段编写有针对性的测试。
- 设计针对任务的评估：让测试反映模型在真实场景分布中的能力。
- 记录一切：在开发过程中进行记录，以便从日志中挖掘出有价值的评估用例。
- 尽可能实现自动化：构建评估流程以便支持自动评分。
- 这是一个过程，而不是终点：评估是一个持续进行的过程。
- 保持一致性：利用人类反馈来校准自动评分。

**反模式**



- 指标过于宽泛：仅依赖困惑度或 BLEU 分数等学术指标。
- 存在偏差的设计：所构建的评估数据集未能真实再现生产环境中的流量模式。
- 凭感觉的评估：将“看起来能用”作为评估策略，或者等到上线之后才开始实施任何评估。
- 忽视人工反馈：未根据人工评估来校准自动化指标。

## 设计你的评估流程

评估工作流中有几个重要组件：

1. **定义评估目标**。评估的成功标准是什么？
1. **收集数据集**。哪些数据有助于你根据目标进行评估？可考虑合成评估数据、特定领域的评估数据、购买的评估数据、人工整理的评估数据、生产数据和历史数据。
1. **定义评估指标**。你将如何检查是否达到成功标准？
1. **运行并比较评估**。针对你的任务或系统反复迭代并提升模型性能。
1. **持续评估**。设置持续评估 (CE)，以便在每次变更时运行评估；监控你的应用以识别新的非确定性案例，并持续扩充评估集。

让我们来看几个示例。

### 示例：总结转录文本

若要测试基于 LLM 的应用在转录文本摘要方面的能力，评估设计可以如下所示：

1. **定义评估目标**

   模型应在相关性和准确性方面能够与参考摘要相竞争。
1. **收集数据集**

   结合使用生产数据（从用户对生成摘要的反馈中收集）和由领域专家（作者）创建的数据集，来确定一个“好的”摘要。
1. **定义评估指标**

   在 1000 条参考转录文本→摘要的保留集上，该实现应使用 G-Eval 达到至少 0.40 的 ROUGE-L 分数和至少 80% 的连贯性分数。
1. **运行并比较评估**

   使用 [Evals API](https://developers.openai.com/api/docs/guides/evals) 在 OpenAI 控制台中创建并运行评估。
1. **持续评估**

   设置持续评估（CE），以便在每次变更时运行评估，监控你的应用以识别新的不确定性情况，并随着时间推移不断扩充评估集。

LLM 更擅长在选项之间进行辨别。因此，评估
  应聚焦于两两对比、分类或针对特定标准打分等
  任务，而不是开放式生成。让评估方法与
  LLM 在比较方面的优势对齐，可以更可靠地
  评估 LLM 输出或模型对比。

### 示例：基于文档的问答

要测试基于 LLM 的应用对文档进行问答的能力，你的评估设计可以是这样的：

1. **定义评估目标**

   该模型应能提供精确的回答，根据需要回忆上下文以推理用户提示，并给出满足用户需求的答案。
1. **收集数据集**

   混合使用生产数据（从用户对所提供回答的满意度中收集）、由领域专家创建的问题的硬编码正确答案以及来自日志的历史数据。
1. **定义评估指标**

   上下文召回率不低于 0.85，上下文精确率高于 0.7，且 70% 以上的回答获得正面评价。
1. **运行并比较评估**

   使用 [Evals API](https://developers.openai.com/api/docs/guides/evals) 在 OpenAI 控制台中创建并运行评估。
1. **持续评估**

   设置持续评估（CE），以便在每次变更时运行评估，监控你的应用以识别新的不确定性情况，并随着时间推移不断扩充评估集。

在创建评估数据集时， 
  [`gpt-6-astra`](https://developers.openai.com/api/docs/models/gpt-6-astra) 
  可用于收集评估示例和边界情况。可以考虑使用它来
  帮助你生成覆盖多种场景的多样化测试数据。确保
  你的测试数据包含典型用例、边界用例和对抗性用例。使用
  人类专家进行标注。

## 确定你需要评估的位置

从简单架构到更复杂的架构，复杂度会随之增加。以下是四种常见的架构模式：

- [单轮模型交互](#single-turn-model-interactions)
- [工作流](#workflow-architectures)
- [单智能体](#single-agent-architectures)
- [多智能体](#multi-agent-architectures)

阅读下方每种架构，找出系统中非确定性出现的位置。那就是你需要实现评估的地方。

### 单轮模型交互

在这种架构中，用户向模型提供输入，模型会处理这些输入（以及提供的任何开发者提示），并生成相应的输出。

#### 示例

举个例子，考虑一个在线零售的场景。你的系统提示指示模型 **对客户的问题进行分类** 为以下类别之一：

- `order_status`
- `return_policy`
- `technical_issue`
- `cancel_order`
- `other`

为了确保一致、高效的用户体验，模型应当 **只返回与用户意图匹配的标签**。假设客户问道：“我的订单状态如何？”

### 工作流架构

当你着手解决更复杂的问题时，可能会从单轮模型交互过渡到多步骤的工作流，将多个模型调用串联起来。工作流不会引入任何新的不确定性元素，但它们涉及多个底层模型交互，你可以对其进行单独评估。

#### 示例

沿用之前的同一个例子，客户询问其订单状态。工作流架构会对客户请求进行分流，并通过一个逐步的流程来路由处理：

1. 提取订单 ID
1. 查询订单详情
1. 将订单详情提供给模型以生成最终回复

此工作流中的每个步骤都有自己的系统提示，模型必须遵循该提示，并将所有获取的数据整合为友好的输出。

### 单智能体架构

与工作流不同，智能体解决需要灵活决策的非结构化问题。智能体拥有指令和一组工具，并动态选择要使用的工具。这引入了一种新的不确定性。

工具是开发者定义的、可由模型执行的代码块。这
  可以是从简单辅助函数到调用现有服务的API调用。例如，
  例如， `check_order_status(order_id)` 可以是一个工具，它接受
  参数 `order_id` 并调用 API 来检查订单状态。

#### 示例

让我们改造前面客户服务示例，让其使用单个智能体。该智能体可以访问三个不同的工具：

### 多智能体架构

当你在单一智能体架构中不断增加工具和任务时，模型可能会难以遵循指令或选择正确的工具来调用。多智能体架构通过创建多个专注于不同领域的独立智能体来解决这个问题。这种在多个智能体之间的分诊与交接带来了一种新的不确定性。

是否使用多智能体架构，应当由你的评估结果来决定。
  一开始就采用多智能体架构会引入不必要的复杂性，可能
  拖慢你的上线时间。

## 创建并组合不同类型的评估器

在设计你自己的评估时，有几种特定的评估器类型可供选择。换一种思路来说，就是你希望评估器扮演什么角色。

### 基于指标的评估

量化评估提供一个数值分数，你可以用它来过滤和排序结果。它们为自动化回归测试提供了有用的基准。

- **示例**：精确匹配、字符串匹配、ROUGE/BLEU 评分、函数调用准确性、可执行评估（通过执行来评估功能或行为——例如 text2sql）
- **挑战**：可能未针对特定用例定制，可能遗漏细微差别

### Human evals

人工判断评估提供最高的质量，但速度慢且成本高。

- **示例**：快速浏览系统输出，粗略判断输出质量是更好还是更差；创建一个随机的、盲测的评估流程，让员工、合同工或外包标注机构对系统输出的质量进行评判（例如，对一组候选输出进行排序，或为每个输出打分 1-5）
- **挑战**：人类专家之间存在分歧，成本高、速度慢
- **建议**:
  - 进行多轮细致的人工评审，以优化评分标准
  - 通过提供不同评分等级示例（例如 10 分制中的 1、3 和 8 分），实行"展示而非告知"的策略
  - 在数值评分之外，增加一个通过/未通过的门槛
  - 汇总多位评审人员意见的简单方法是采取多数投票

### LLM-as-a-judge 和模型评分器

使用模型来评判输出比人工评估运行成本更低且更具可扩展性。 [`gpt-6-astra`](https://developers.openai.com/api/docs/models/gpt-6-astra) 在需要强大的大语言模型评判器时使用，然后在针对成本或延迟进行优化之前，先针对人工标签验证一致性。

- **示例**:
  - 成对比较：向裁判模型展示两个回答，并让其根据特定标准判断哪一个更好
  - 单一回答评分：裁判模型在隔离状态下评估单个回答，根据预定义的质量指标为其打分或评级
  - 参考引导式评分：向裁判模型提供一个参考答案或“黄金标准”答案，作为评估给定回答的基准
- **挑战**：位置偏差（回答顺序）、冗长偏差（倾向于更长的回答）
- **建议**:
  - 使用成对比较或通过/不通过以获得更高的可靠性
  - 尽可能使用能力最强的模型进行评分。从 [`gpt-6-astra`](https://developers.openai.com/api/docs/models/gpt-6-astra)，开始，然后验证专门的推理模型在你的评分标准或参考答案集上是否表现更好
  - 控制回答长度，因为 LLM 通常偏向于更长的回答
  - 加入推理与思维链，因为评分前的推理能够提升评估表现
  - 一旦 LLM 裁判在速度、成本和与人工标注的一致性上达到要求，就扩大规模
  - 设计问题结构以支持自动评分，同时保持任务完整性——一种常见做法是将问题改写为多选题形式
  - 确保评估评分标准清晰且详细

没有一种策略是完美的。LLM 作为评判者的质量因问题上下文而异，而使用专家人工标注者提供真实标签既昂贵又耗时。

## 处理边界情况

虽然你的评估应覆盖每种架构的主要、正常路径场景，但现实中的 AI 系统经常会遇到挑战系统性能的边缘情况。评估这些边缘情况对于确保可靠性和良好的用户体验非常重要。

我们看到这些边缘情况可以分为几类：

### 输入差异性

由于用户会向模型提供输入，我们的系统必须具备足够的灵活性，以应对用户可能采用的不同交互方式，例如：

- 非英语或多语言输入
- 输入文本以外的格式（例如 XML、JSON、Markdown、CSV）
- 输入模态（例如图像）

用于指令遵循和功能正确性的评估需要兼容用户可能尝试的输入。

### 上下文复杂度

许多基于大语言模型的应用之所以失败，是因为对请求上下文的理解不足。这些上下文可能来自用户，也可能来自过往对话历史中的干扰信息。

示例包括：

- 单个请求中包含多个问题或意图
- 拼写错误和笔误
- 上下文较少的简短请求（例如，用户只说：“returns”）
- 长上下文或长时间运行的对话
- 返回数据中属性名称含义不清的工具调用（例如， `"on: 123"`，其中 “on” 是订单号）
- 多个工具调用，有时会导致参数错误
- 多次智能体交接，有时会导致循环交接

### 个性化和定制化

虽然 AI 通过适配用户的具体请求来改善用户体验,但这种灵活性也带来了许多边界情况。请针对你希望明确支持或屏蔽的具体用例定义清晰的评估。

- 试图让模型执行不同操作的越狱请求
- 格式要求（例如，格式化为 JSON，或使用项目符号列表）
- 用户提示与你的系统提示冲突的情况

## 使用评估来提升性能

当你的 evals 达到一定成熟度，能够稳定衡量性能时，就可以转而利用 evals 数据来提升应用的性能。

了解有关 [强化微调](https://developers.openai.com/api/docs/guides/reinforcement-fine-tuning) 以构建数据飞轮。
