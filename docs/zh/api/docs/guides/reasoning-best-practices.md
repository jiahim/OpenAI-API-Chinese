# 推理最佳实践

> 完整文档索引请参阅 [llms.txt](/llms.txt)。可通过在页面 URL 末尾追加 `.md` 来获取 Markdown 版本的文档页面。

OpenAI 提供两种类型的模型： [推理模型](https://developers.openai.com/api/docs/models#o4-mini) （例如 o3 和 o4-mini）以及 [GPT 模型](https://developers.openai.com/api/docs/models#gpt-4.1) （如 GPT-4.1）。这些模型系列的行为有所不同。

本指南涵盖：

1. 我们的推理与非推理 GPT 模型之间的差异
1. 何时使用我们的推理模型
1. 如何有效地对推理模型进行提示

详细了解 [推理模型](https://developers.openai.com/api/docs/guides/reasoning) 及其工作原理。

## 推理模型与 GPT 模型

与 GPT 模型相比，我们的 o 系列模型在不同的任务上表现出色，并且需要不同的提示。两个模型系列之间并无优劣之分——它们只是有所不同。

我们训练 o 系列模型（“规划者”）时，让它们对复杂任务进行更长时间、更深入的思考，从而使它们能够有效地制定策略、为复杂问题规划解决方案，并在面对大量模糊信息时做出决策。这些模型还能够高精度、高准确率地执行任务，因此非常适合那些通常需要人类专家的领域——例如数学、科学、工程、金融服务和法律服务。

另一方面，我们延迟更低、成本效益更高的 GPT 模型（“主力模型”）则专为简单直接的执行而设计。一个应用可能会使用 o 系列模型来规划解决问题的策略，并使用 GPT 模型来执行具体任务，尤其是在速度和成本比完美准确率更重要的情况下。

### 如何选择

对你的使用场景来说，最重要的是什么？

- **速度和成本** → GPT 模型速度更快，成本通常更低
- **执行明确定义的任务** → GPT 模型善于处理明确定义的任务
- **准确性和可靠性** → o-series 模型是可靠的决策者
- **复杂问题求解** → o-series 模型能够应对模糊性和复杂性

如果在完成任务时，速度和成本是最重要的因素 _并且_ 你的用例由简单明确的任务组成，那么我们的 GPT 模型最适合你。但是，如果准确性和可靠性是最重要的因素 _并且_ 你需要解决一个非常复杂的多步骤问题，那么我们的 o-series 模型可能更适合你。

大多数 AI 工作流会同时使用这两种模型——o-series 负责智能体规划和决策，GPT 系列负责任务执行。

![GPT 模型与 o-series 模型配合良好](https://cdn.openai.com/API/docs/images/customer-service-example.png)




_我们的 GPT-4o 和 GPT-4o mini 模型根据客户信息对订单详情进行分类，识别订单问题和退货政策，然后将这些数据点全部输入 o3-mini，由其根据政策对退货的可行性做出最终决定。_




## 何时使用我们的推理模型

以下是我们从客户以及 OpenAI 内部观察到的一些成功使用模式。这并不是对所有可能用例的全面综述，而是为测试我们的 o 系列模型提供的一些实用指导。

[准备好使用推理模型了吗？跳转到快速入门 →](https://developers.openai.com/api/docs/guides/reasoning)

### 1. 处理含糊不清的任务

推理模型特别擅长在信息有限或来源零散的情况下，仅凭一个简单的提示就能理解用户意图并处理指令中的任何空白。事实上，推理模型在做出未经充分判断的猜测或尝试填补信息空白之前，通常会主动提出澄清性问题。

> “o1 的推理能力使我们的多智能体平台 Matrix 能够在处理复杂文档时生成详尽、格式规范且详细的回复。例如，o1 使 Matrix 仅通过一个基础提示就能轻松识别信贷协议中受限付款额度下可用的篮子。没有其他模型能表现得如此出色。在密集型信贷协议的复杂提示上，o1 相较于其他模型在 52% 的提示上产生了更强的结果。”
>
> —[Hebbia](https://www.hebbia.com/)，面向法律与金融的 AI 知识平台公司

### 2. 大海捞针

在传递大量非结构化信息时，推理模型非常擅长理解并仅提取与回答问题最相关的信息。

> "为了分析一家公司的收购，o1 审阅了数十份公司文档——例如合同和租约——以查找任何可能影响该交易的棘手条件。该模型负责标记关键条款，在此过程中，它在脚注中发现了一项至关重要的"控制权变更"条款：如果该公司被出售，则必须立即偿还一笔 7500 万美元的贷款。o1 对细节的极度关注使我们的 AI 智能体 能够通过识别关键任务信息来为金融专业人士提供支持。"
>
> —[Endex](https://endex.ai/)，AI 金融情报平台

### 3. 在大型数据集中发现关系与细微差异

我们发现，推理模型在处理复杂文档方面表现出色，这些文档通常包含数百页密集且非结构化的信息，例如法律合同、财务报表和保险理赔单。这些模型尤其擅长在不同文档之间寻找相似之处，并根据数据中隐含的线索做出决策。

> “税务研究需要综合多份文档才能得出最终且条理清晰的答案。我们将 GPT-4o 替换为 o1 后，发现 o1 在跨文档推理、得出任何单一份文档都看不出的逻辑结论方面表现出色。因此，切换到 o1 后，我们在端到端性能上获得了 4 倍的提升——非常惊人。”
>
> —[Blue J](https://www.bluej.com/)，用于税务研究的 AI 平台

推理模型同样擅长对细致的策略和规则进行推理，并将它们应用于当前任务，从而得出合理的结论。

> "在财务分析中，分析师经常需要处理围绕股东权益的复杂场景，并理解其中相关的法律细节。我们使用一个具有挑战性但很常见的问题，测试了来自不同提供商的约 10 个模型：一轮融资会如何影响现有股东，尤其是在他们行使反稀释特权时？这需要对投前和投后估值进行推理，并处理循环稀释问题——即使是顶级财务分析师也需要 20 到 30 分钟才能理清。我们发现 o1 和 o3-mini 可以毫无瑕疵地完成这项任务！这些模型甚至生成了一张清晰的计算表，展示了融资对一位持有 10 万美元股份的股东所产生的影响。"
>
> –[BlueFlame AI](https://www.blueflame.ai/)，面向投资管理的 AI 平台

### 4. 多步智能体规划

推理模型对智能体的规划和策略制定至关重要。我们观察到，当推理模型被用作“规划者”（planner）时效果显著：它会针对问题生成详细的多步骤解决方案，然后根据每个步骤对高智能或低延迟的需求，选择并分配合适的 GPT 模型作为“执行者”（doer）。

> “我们在 智能体 基础设施中将 o1 用作规划器，让它在 工作流 中编排其他模型以完成多步骤任务。我们发现 o1 非常擅长选择数据类型并将大问题拆分成更小的部分，使其他模型能够专注于执行。”
>
> —[Argon AI](https://argon-ai.com/)，面向制药行业的 AI 知识平台

> “o1 为 Lindy（我们的工作 AI 助手）中的许多智能体工作流提供动力。该模型使用函数调用从你的日历或电子邮件中提取信息，然后可以自动帮助你安排会议、发送邮件并管理日常任务的其他部分。我们将过去经常出问题的所有智能体步骤都切换到了 o1，结果我们的 智能体 几乎在一夜之间变得毫无瑕疵！”
>
> —[Lindy.AI](http://Lindy.AI)，工作的 AI 助手

### 5. 视觉推理

截至目前，o1 是唯一支持视觉能力的推理模型。它与 GPT-4o 的区别在于，o1 即使在最复杂的视觉内容（例如结构不清晰的图表和表格，或图像质量不佳的照片）面前也能准确理解。

> “我们为在线的数百万产品自动化风险与合规审查，包括奢侈品仿制品、濒危物种和管制物质。GPT-4o 在我们最难的图像分类任务上达到了 50% 的准确率。o1 在不对我们的流水线做任何修改的情况下，取得了令人印象深刻的 88% 准确率。”
>
> —[SafetyKit](https://www.safetykit.com/)，AI 驱动的风险与合规平台

从我们自身的内部测试来看，我们发现 o1 能够从高度详细的建筑图纸中识别出构件和材料，从而生成一份全面的材料清单。我们观察到的最令人惊讶的事情之一是，o1 能够跨不同图像进行类比推理，例如将建筑图纸某一页中的图例正确地应用到另一页上，且无需明确指令。如下图所示，针对 4x4 PT 木柱，o1 根据图例识别出 "PT" 代表压力处理（pressure treated）。

### 6. 审查、调试与提升代码质量

推理模型在审查和改进大量代码方面特别有效，由于模型的延迟较高，通常会在后台运行代码审查。

> “我们在 GitHub 和 GitLab 等平台上提供自动化 AI 代码审查服务。虽然代码审查流程本身对延迟并不敏感，但它需要理解跨多个文件的代码差异。这正是 o1 真正擅长的领域——它能够可靠地检测出代码库中那些可能被人工审查员忽略的细微改动。在切换到 o 系列模型之后，我们的产品转化率提升了三倍。”
>
> —[CodeRabbit](https://www.coderabbit.ai/)，AI 代码审查创业公司

虽然 GPT-4o 和 GPT-4o mini 因其更低的延迟可能更适合编写代码，但我们也看到 o3-mini 在对延迟敏感度稍低的代码生成用例中表现突出。

> “o3-mini 能够持续产出高质量、可直接落地的代码，并且在问题定义明确时，即使面对极具挑战的编码任务，也常常能够给出正确解法。其他模型可能只适用于小规模、快速的代码迭代，而 o3-mini 在规划与执行复杂软件设计系统方面表现出色。”
>
> —[Windsurf](https://codeium.com/)，一款由 Codeium 构建的协作型智能体驱动 AI IDE

### 7. 针对其他模型响应的评估与基准测试

我们也看到推理模型在基准测试和评估其他模型响应方面表现出色。数据验证对于确保数据集的质量和可靠性至关重要，尤其是在医疗等敏感领域。传统的验证方法使用预定义的规则和模式，而像 o1 和 o3-mini 这样先进的模型能够理解上下文并对数据进行推理，从而提供更灵活、更智能的验证方法。

> "许多客户在 Braintrust 的评估流程中使用 LLM-as-a-judge。例如，一家医疗公司可能会使用 gpt-4o 这类主力模型来总结患者问题，然后使用 o1 评估摘要质量。一位 Braintrust 客户的 judge F1 分数从使用 4o 时的 0.12 提升到使用 o1 时的 0.74！在这些用例中，他们发现 o1 的推理能力在处理最困难、最复杂的评分任务时，能够敏锐捕捉 completions 之间的细微差异，堪称改变游戏规则。"
>
> —[Braintrust](https://www.braintrust.dev/)，AI 评估平台

## 如何有效地对推理模型进行提示

这些模型在简单直接的提示下表现最佳。一些提示工程技巧（例如指示模型“逐步思考”）可能无法提升性能（有时甚至会降低性能）。请参阅下面的最佳实践，或者 [从提示示例开始](https://developers.openai.com/api/docs/guides/reasoning#advice-on-prompting).

- **开发者消息是新的系统消息**：从开始 `o1-2024-12-17`，推理模型支持开发者消息而非系统消息，以与所述的指挥链行为保持一致 [模型规范](https://cdn.openai.com/spec/model-spec-2024-05-08.html#follow-the-chain-of-command).
- **保持提示简洁直接**：这些模型擅长理解和响应简短、清晰的指令。
- **避免使用思维链提示**：由于这些模型在内部进行推理，因此无需提示它们“逐步思考”或“解释你的推理过程”。
- **使用分隔符以提高清晰度**：使用 Markdown、XML 标签和章节标题等分隔符来明确标示输入的不同部分，帮助模型恰当地解读各个部分。
- **先尝试零样本，如果需要再使用少样本**: 推理模型通常不需要少样本示例就能产生良好的结果，因此先尝试编写不含示例的提示。如果对期望输出有更复杂的要求，在提示中加入一些输入和期望输出的示例可能会有所帮助。但请确保示例与你的提示说明高度一致，因为两者之间的差异可能导致结果不佳。
- **提供具体的指引**: 如果你有明确想要约束模型响应的方式（例如“提出一个预算低于 500 美元的方案”），请在提示中明确列出这些约束条件。
- **非常具体地说明你的最终目标**: 在你的说明中，尽量为成功响应给出非常具体的参数，并鼓励模型持续推理和迭代，直到匹配你的成功标准。
- **Markdown 格式**：从开始 `o1-2024-12-17`，推理模型在 API 中会避免生成带有 markdown 格式的响应。若希望模型在响应中使用 markdown 格式，请在开发者消息的第一行加入字符串 `Formatting re-enabled` 。

## 如何兼顾低成本与高精度

随着 `o3` 并且 `o4-mini` 模型的推出，Responses API 中持久化的推理项的处理方式有所不同。在此之前（对于 `o1`, `o3-mini`, `o1-mini` 并且 `o1-preview`），即使推理项被包含在请求的输入项中，在后续的 API 请求中它们也总是会被忽略。在 `o3` 并且 `o4-mini`，下，与函数调用相邻的某些推理项会被纳入模型的上下文，以在使用尽可能少的推理 token 的同时提升模型性能。

为了在使用此变更时获得最佳效果，我们推荐使用 [Responses API](https://developers.openai.com/api/reference/resources/responses) 并将 `store` 参数设置为 `true`，同时传入来自之前请求的所有推理项（可以使用 `previous_response_id`，也可以取出一个旧请求的所有输出项并作为输入项传入新请求）。OpenAI 会自动将相关的推理项纳入模型的上下文，并忽略不相关的推理项。在更高级的使用场景中，如果你希望更精确地管理进入模型上下文的内容，我们建议你至少包含从最近一次函数调用到上一次用户消息之间的所有推理项。这样做可以确保模型在响应函数调用时不必重新开始推理，从而获得更好的函数调用性能并降低整体 token 使用量。

如果你使用的是 Chat Completions API，推理项则永远不会纳入模型的上下文。这是因为 Chat Completions 是一个无状态的 API。这会导致在涉及多次函数调用的复杂智能体场景下，模型性能略有下降且推理 token 使用量增加。在不涉及复杂的多重函数调用的场景中，无论使用哪种 API，性能都不应出现下降。
